

#### 一、先明确同城双活的核心设计原则

所有维度的设计均需围绕以下原则展开，避免方案偏离核心目标：

- 无状态化优先：应用层尽可能实现无状态，将会话、配置等抽离至共享存储 / 中间件，降低切换复杂度；
- 数据一致性为核心：根据业务等级（核心交易 / 非核心查询）定义一致性级别（强一致 / 最终一致），杜绝数据丢失、脏写；
- 对等部署：双机房（A/B）做到软硬件配置对等、网络带宽对等、算力资源对等、运维能力对等，避免 “主备” 式资源失衡；
- 故障隔离：双机房实现电力、网络、制冷、物理地域的故障隔离（如不同变电站、不同光纤路由），杜绝单点故障扩散；
- 自动化为主：切换、扩容、故障检测均实现自动化，减少人工介入的延迟和误操作；
- 最小影响：日常演练、故障切换对业务的影响控制在秒级 / 毫秒级，满足 SLA 要求（如金融行业要求 RTO≤5min、RPO=0）。


#### 二、基础设施层：双机房的基础保障（同城双活的前提）

基础设施是同城双活的 “地基”，若机房层存在单点，后续所有设计均无意义，核心设计要点：
1. 机房物理部署
- 双机房距离控制在30-50km内，既保证网络时延≤5ms（满足数据同步、应用交互），又实现物理故障隔离；
- 避免同一片园区 / 写字楼，需做到不同电力供应（独立变电站）、不同光纤运营商、不同制冷系统。

2. 算力与存储资源
- 对等扩容：A/B 机房的服务器（CPU / 内存 / 磁盘）、虚拟化资源（K8s 节点 / VM）按 1:1 配置，核心业务预留≥30% 的冗余资源；
- 存储双活：采用分布式存储（如 Ceph / 华为 OceanStor）、存储阵列双活（如 IBM SVC），实现存储层的跨机房镜像，支持秒级切换；
- 资源池化：将双机房的算力、存储整合成统一资源池，由云管平台（如 OpenStack / 阿里云管）调度，实现资源的跨机房弹性分配。

3. 电力与制冷
双机房均配置双路市电 + UPS + 柴油发电机，UPS 续航≥30min，发电机启动时间≤5min，满足突发断电的应急需求；
制冷系统采用N+1 冗余，避免单台空调故障导致机房温湿度超标。

##### 三、网络层：跨机房的通信与访问核心（同城双活的血脉）

同城双活的网络层需解决跨机房数据同步带宽、业务访问路由、故障切换时的网络漂移、网络隔离四大问题，核心设计要点：

1. 跨机房骨干网络

- 带宽规划：按核心业务数据同步峰值 + 日常业务交互流量的 2 倍规划跨机房互联带宽（如交易峰值同步流量 10G，互联带宽配置 20G），采用裸光纤 / 波分复用（WDM），保障低时延、高可靠；

- 带宽冗余：配置双运营商、双路由的跨机房光纤，做到主备路由自动切换，避免单光纤中断；

- 时延控制：通过网络优化（如关闭不必要的网络协议、开启 Jumbo Frame）将跨机房时延控制在 **≤5ms**，满足数据库同步（如 MySQL MGR）、中间件集群（如 Kafka）的需求。

2. 业务访问路由

- 公网接入：采用DNS 智能解析（如阿里云 DNS/CloudFlare）+ Anycast 公网 IP，实现用户请求的就近接入 + 故障自动漂移；
- 内网访问：核心业务采用三层负载均衡（如 F5 / 华为 AD）+ 容器服务 Ingress，构建跨机房的统一负载均衡层，支持将请求分发至 
A/B 机房的应用节点；
- IP 规划：双机房采用统一的内网网段规划（如同一 VPC / 子网），避免跨机房访问的 NAT 转换，减少时延和复杂度；

- 会话保持：无状态应用通过负载均衡的 cookie 会话保持，有状态应用通过分布式会话中间件（如 Redis 集群） 实现跨机房会话共享。

3. 网络隔离与安全

- 微分段：通过网络微分段（如 Cisco ACI / 华为 CloudFabric）将业务按等级（核心 / 非核心）划分安全域，跨机房访问需经过防火墙策略控制；

- 跨机房防护：双机房部署对等的防火墙、WAF、IDS/IPS、抗 DDoS 设备，避免单机房防护缺失导致全网受攻击；

- 网络监控：对跨机房互联带宽、时延、丢包率进行实时监控，阈值触发时自动告警并切换备路由。

四、数据层：同城双活的核心难点（重中之重）

数据层是同城双活的 “核心痛点”，尤其是关系型数据库的跨机房同步，需根据业务一致性要求做差异化设计，核心设计要点按数据类型拆解：
核心原则：按业务等级定义数据一致性（RPO/RTO）

业务等级	一致性要求	适用场景	典型技术
核心交易（如支付 / 转账）	强一致（RPO=0、RTO≤30s）	金融交易、政务办事、电商下单	数据库集群（MGR/PolarDB）、分布式事务（Seata）

非核心查询（如商品列表 / 日志）	最终一致（RPO≤5min）	大数据分析、静态页面、非实时查询	主从同步、消息队列（Kafka）、数据
同步工具（DataX）

1. 关系型数据库（MySQL/Oracle/PostgreSQL）

（1）强一致性设计（核心交易首选）
- 原生集群方案：采用分布式集群架构，跨机房部署节点，实现数据多副本同步：
  + MySQL：采用MGR（MySQL Group Replication），A/B 机房各部署 2 个节点 + 1 个仲裁节点（可部署在第三方轻量机房），满足多主写入、强一致；
  + Oracle：采用RAC 跨机房部署（2+2 节点），结合 ASM 共享存储，实现双机房的主主写入；
  + 国产数据库：达梦 / 人大金仓采用集群跨机房部署，利用原生的同步协议实现强一致。
  + 分布式事务：跨库 / 跨服务的核心交易，采用Seata AT/TCC 模式或数据库原生分布式事务，杜绝跨机房的事务不一致。

（2）最终一致性设计（非核心业务）
- 采用主主同步（双写）+ 冲突解决：A/B 机房数据库互为主从，通过主键自增规则（如 A 机房奇数、B 机房偶数）、乐观锁解决脏写冲突；

- 同步工具：使用Canal/Debezium解析 binlog，结合 Kafka 实现跨机房的准实时同步，时延控制在秒级。

2. 非关系型数据库（Redis/MongoDB/Elasticsearch）
- Redis：核心业务采用Redis Cluster 跨机房部署（A/B 机房各部署一半主节点，从节点交叉部署），开启持久化 + 主从同步，实现故障自动主从切换；非核心业务采用主主同步（如 Redis Sentinel 双主）；

- MongoDB：采用Replica Set 跨机房部署（主节点在 A、从节点在 B、仲裁节点第三方），开启 oplog 同步，实现秒级故障切换；
- Elasticsearch：采用跨机房分片部署（主分片在 A、副分片在 B），副本数≥1，实现数据的跨机房冗余，查询请求可分发至双机房。

3. 数据同步的通用设计要点

- 同步链路冗余：所有数据同步链路均配置主备双链路，避免单链路中断导致数据同步失败；
- 冲突解决机制：必须设计主键规则、乐观锁、时间戳、版本号等冲突解决方案，杜绝双写导致的数据脏读 / 脏写；
- 同步监控：实时监控数据同步的时延、丢包、同步失败数，阈值触发时自动暂停写入并告警，避免数据不一致扩散；
- 数据校验：定时通过数据比对工具（如 MySQL pt-table-checksum） 校验双机房数据一致性，发现差异自动修复。

#### 五、应用层：无状态化与服务化（降低切换复杂度）

应用层的设计目标是尽可能无状态、服务化，让应用节点可以在 A/B 机房随意调度，核心设计要点：

1. 应用无状态化改造

- 所有会话数据、用户配置、临时数据抽离至分布式缓存（Redis）、共享存储（NFS / 分布式存储），应用节点仅处理业务逻辑，不存储任何 本地数据；

- 配置中心统一化：采用Nacos/Apollo/ConfigMap实现跨机房的配置统一管理，配置修改实时同步至双机房的应用节点，避免配置不一致。

2. 微服务架构适配（主流架构）

- 基于Spring Cloud/K8s/Dubbo构建微服务，将业务拆分为独立的微服务，每个微服务在 A/B 机房对等部署（节点数 1:1）；
服务注册发现：采用Nacos/Eureka/CoreDNS实现跨机房的服务注册发现，注册中心跨机房集群部署（A/B 机房各节点），避免注册中心单点；

- 服务调用：微服务之间通过服务名调用，由注册中心自动解析至双机房的可用节点，支持故障自动剔除（如 Sentinel/Hystrix）。

3. 应用部署与调度

- 容器化部署：所有应用采用Docker/K8s容器化部署，将双机房的 K8s 集群整合成跨机房联邦集群（K8s Federation），实现应用 Pod 的跨机房调度、扩容；

- 灰度发布与演练：基于 K8s 实现跨机房的灰度发布，日常容灾演练可在 B 机房进行，不影响 A 机房的核心业务；

- 应用健康检查：配置细粒度的健康检查规则（如业务接口检查 > 端口检查 > 进程检查），K8s / 负载均衡可自动剔除故障节点，实现故障自愈。

#### 六、中间件层：跨机房的集群化部署（承上启下）

消息队列、分布式任务、服务网格等中间件是应用层和数据层的 “桥梁”，需做到跨机房集群化、无单点、消息不丢失，核心设计要点：

1. 消息队列（Kafka/RabbitMQ/RocketMQ）

- Kafka：跨机房部署Kafka Cluster，A/B 机房各部署 broker 节点，主题分区的主副本交叉部署（主分区在 A、副分区在 B），开启acks=all保证消息不丢失；

- RocketMQ：采用主从集群跨机房部署，NameServer 集群双机房对等部署，实现消息的跨机房同步，支持故障自动切换；

- 核心要求：消息队列需保证至少一次投递，避免跨机房消息丢失，非核心业务可采用最终一致。

2. 其他中间件

- 分布式任务（XXL-Job/Elastic-Job）：调度中心跨机房集群部署，执行器双机房对等部署，通过分片策略避免任务重复执行；

- 服务网格（Istio/Linkerd）：跨机房部署服务网格，实现微服务的流量治理、熔断降级、跨机房流量调度，简化应用层的网络逻辑；

- 配置中心 / 注册中心：均采用3 节点及以上的跨机房集群（如 A 机房 2 节点、B 机房 1 节点），保证集群高可用，配置 / 服务信息实时同步。

#### 七、容灾切换层：自动化的故障检测与切换（落地核心）

同城双活的价值最终体现在故障切换的效率，需设计分级、自动化、可演练的切换方案，核心设计要点：

1. 故障分级与切换策略
按故障影响范围划分等级，对应不同的切换策略，避免 “小故障大切换”：

故障等级	故障场景	切换策略
一级（单节点 / 单服务）	单应用节点、单数据库从节点故障	自动剔除故障节点，由双机房其他节点承接流量，无需机房级切换
二级（单机房局部）	单机房某安全域、某中间件集群故障	自动将该域的流量漂移至另一机房，其余业务保持原接入
三级（单机房整体）	单机房电力、网络、制冷全面故障	全业务机房级切换，所有流量漂移至另一机房

2. 自动化切换流程

设计端到端的自动化切换链路，核心步骤：

- 故障检测：通过监控系统（如 Prometheus/Zabbix）对机房、网络、数据库、应用做秒级检测，触发故障阈值（如时延 > 100ms、节点离线 > 30s）；

- 故障确认：通过多维度校验（如不同监控节点均检测到故障）避免误判，确认后触发切换；

- 流量漂移：DNS / 负载均衡自动将用户请求从故障机房漂移至健康机房，同时关闭故障机房的写入权限；

- 数据校验：同步校验双机房数据一致性，确认无差异后开放健康机房的全量业务；

- 故障恢复：故障解决后，通过灰度方式将流量切回，同时同步数据，恢复双活状态。

3. 切换方式设计

- 手动切换：用于日常演练、计划性维护（如机房扩容、系统升级），由运维通过操作平台触发，支持灰度切流；

- 自动切换：用于突发故障（如机房断电、网络中断），无需人工介入，秒级完成；

- 强制切换：用于数据一致性异常的极端场景，强制将流量切至健康机房，同时冻结故障机房的所有操作。

4. 容灾演练

- 常态化演练：每月进行一级 / 二级故障演练，每季度进行三级机房级切换演练，演练过程对业务无感知；
- 演练复盘：每次演练后复盘切换时长、数据一致性、故障检测延迟，优化方案；
- 演练环境：搭建与生产一致的演练环境，避免演练影响生产数据。

#### 八、运维监控层：可观测性是双活的保障（提前发现问题）

同城双活的复杂度远高于单机房，若缺乏全维度、跨机房的监控，会导致故障发现晚、定位慢，核心设计要点：

1. 全链路监控覆盖
实现从用户请求到基础设施的端到端监控，无监控盲区：

- 业务层：监控交易成功率、响应时间、TPS/QPS、报错率，按双机房拆分指标；

- 应用层：监控应用节点的 CPU / 内存 / 磁盘、接口调用情况、JVM 状态，跨机房对比；

- 中间件层：监控消息队列的消息堆积、同步时延，数据库的连接数、锁等待、同步状态；

- 网络层：监控跨机房带宽利用率、时延、丢包率，公网 DNS 解析成功率、负载均衡流量分配；

- 基础设施层：监控机房的电力、制冷、服务器状态、存储使用率，双机房资源池利用率。

2. 监控系统设计

- 跨机房部署：监控系统本身需双机房对等部署，避免监控系统单点导致故障无法发现；

- 统一监控平台：将所有监控指标汇聚至统一平台（如 Grafana / 华为 CloudMonitor），支持双机房指标的对比、告警、可视化；

- 智能告警：采用多维度告警规则（如故障持续时间、指标阈值、影响范围），避免告警风暴；告警方式覆盖短信、电话、企业微信，核心故障触发电话告警。

3. 日志与链路追踪

- 日志统一收集：通过ELK/EFK收集双机房的应用日志、系统日志、数据库日志，实现跨机房的日志检索、分析；

- 全链路追踪：采用SkyWalking/Pinpoint/Zipkin实现微服务的全链路追踪，跨机房的调用链路可一键溯源，快速定位故障点；

- 日志审计：对跨机房的操作（如数据同步、切换、扩容）做全量日志审计，满足合规要求。

4. 自动化运维平台

构建统一的同城双活运维平台，整合以下能力，实现 “一站式操作”：

- 资源调度：跨机房的算力、存储资源分配；

- 切换操作：手动 / 自动切换的触发、监控；

- 容灾演练：演练计划制定、执行、复盘；

- 数据管理：数据同步、校验、修复；

- 告警管理：告警规则配置、接收、处理。

#### 九、合规与安全层：满足行业监管要求

金融、政务、医疗等行业对同城双活有明确的监管合规要求，方案设计需同步满足，核心设计要点：

- 数据安全：跨机房的数据同步需采用加密传输（如 SSL/TLS），核心数据（如用户密码、交易数据）需做端到端加密，避免传输过程中泄露；

- 数据备份：同城双活并非 “备份”，需在同城双活的基础上，增加异地容灾备份（如同城双活 + 异地三中心），满足监管 “两地三中心” 要求；

- 操作合规：所有跨机房的操作（如数据修改、切换）需做权限控制、操作审计、审批流程，杜绝越权操作；

- 等保要求：同城双活方案需满足网络安全等级保护（等保 2.0/3.0） 要求，实现安全域隔离、入侵防护、数据备份恢复；
SLA 制定：与业务方、运维方制定明确的SLA 协议，明确 RTO/RPO、切换时长、故障恢复率等指标，作为方案落地和运维的考核标准。

#### 十、非核心但关键的设计要点：成本与资源利用率

同城双活的 1:1 资源配置会导致成本上升，需在高可用和成本之间做平衡，核心优化点：

- 资源弹性调度：利用云原生的弹性伸缩能力，非核心业务在低峰期缩容，高峰期扩容，提高资源利用率；

- 混部部署：在核心业务的冗余资源上，混部非核心、低优先级的业务（如日志分析、大数据计算），避免资源闲置；

- 分级部署：并非所有业务都需要做同城双活，对非核心业务采用 “主备” 模式（如 A 机房主、B 机房备，资源配置 1:0.5），降低成本；

- 存储优化：采用分布式存储替代传统高端存储，降低存储层的成本，同时提高存储的扩展性和可靠性；

- 网络带宽优化：对跨机房的非核心流量（如日志、监控）做压缩、限流、错峰传输，减少跨机房带宽的占用。

#### 十一、同城双活的典型架构参考（落地模板）

结合以上维度，给出通用的同城双活架构模板，适配大部分企业：

同城双机房（A/B）+ 统一资源池 + 跨机房网络骨干 + 无状态应用层 + 分布式数据层 + 自动化切换层 + 异地容灾备份

- 基础设施：A/B 机房对等部署，整合成统一算力 / 存储资源池；

- 网络层：裸光纤跨机房互联，DNS 智能解析 + 跨机房负载均衡实现流量接入；

- 应用层：微服务无状态化，K8s 联邦集群跨机房调度 Pod；

- 数据层：核心数据库采用 MGR/RAC 跨机房集群（强一致），非核心采用主主同步（最终一致），Redis Cluster 跨机房部署；

- 中间件层：Kafka/RocketMQ 跨机房集群，配置 / 注册中心跨机房部署；

- 容灾层：自动化故障检测 + 分级切换，常态化容灾演练；

- 监控层：全链路监控 + 统一日志 + 链路追踪，智能告警；

- 备份层：同城双活 + 异地三中心，满足监管和数据安全要求。


最后：同城双活方案的落地步骤（避免一步到位的坑）

#### 同城双活并非一次性落地，需按业务分级、循序渐进的原则推进，避免因复杂度太高导致项目失败：

- 第一步：业务分级：梳理所有业务，划分核心 / 非核心，明确各业务的一致性、SLA 要求；

- 第二步：基础设施改造：完成双机房的物理隔离、资源池化、跨机房网络搭建；

- 第三步：应用无状态化改造：将核心业务的应用层抽离状态，部署至双机房；

- 第四步：数据层改造：先实现非核心数据的跨机房同步，再推进核心数据的强一致集群部署；

- 第五步：中间件层集群化：将所有中间件跨机房集群部署，实现无单点；

- 第六步：自动化切换与监控：搭建切换平台、统一监控平台，实现故障检测和切换的自动化；

- 第七步：常态化演练：进行分级故障演练，优化方案，逐步提升切换效率；

- 第八步：全业务落地：将非核心业务按分级部署原则落地，最终实现全业务的同城双活。
